# Tag Model

PmmoJS uses NBT tags in several different places. If you look at the perk system alone, you will see tags in at least four different roles. This page explains what each tag does and when to use which one.

## Tag categories

You will encounter two main categories of tags in PmmoJS:

- **Static tags** define data and persist between game sessions. Examples: perk startup defaults, perk config entries.
- **Runtime tags** carry live state for one execution path and disappear after that path finishes. Examples: trigger context, internal hook context, perk execution settings.

The most important rule: when a tag is meant for later lifecycle stages (like `tick()` or `stop()`), write to `ctx.getSettings()`. When a tag is meant only for the current execution pass, write to `ctx.getResult()`.

## Where tags appear

| System | API | Tag type | Lifetime |
|---|---|---|---|
| Startup perk registration | `PmmoJS.registerPerk(...)` | `PerkTagJS` (wraps `CompoundTag`) | Static — becomes the perk's default settings |
| Perk execution callbacks | `ctx.getSettings()`, `ctx.getResult()` | `PerkTagJS` | Runtime — built fresh for each perk execution |
| Trigger hooks | `PmmoJS.trigger(...)` | Mutable `CompoundTag` context | Runtime — one trigger dispatch |
| Internal hooks | `PmmoJS.internal(...)` | Mutable `CompoundTag` context | Runtime — one internal handler dispatch |
| XP event | `PmmoJS.xp(...)` | Raw `CompoundTag` | Runtime — one XP event |
| Perk config editing | `PmmoJS.perksConfig(...)` | Static `CompoundTag` entries | Static — stored in PMMO's config |
| Direct trigger listeners | `PmmoHelper.registerTriggerListener(...)` | Raw `CompoundTag` | Runtime — one listener invocation |

## Perk tags in depth

When you register a perk with `PmmoJS.registerPerk(...)`, the builder methods like `withSkill(...)`, `withCooldown(...)`, and `withInt(...)` write values into a **startup default tag**. This tag defines the perk's initial configuration.

At runtime, PMMO builds a **merged settings tag** for each perk execution by combining these sources in order:

1. Your startup defaults from `registerPerk`
2. The matching entry from `perks.toml` (if any)
3. Incoming data from the current PMMO event
4. Output from earlier perks in the same execution pass

If the merged tag contains a `skill` field, PMMO also injects the current player's level for that skill as a `level` field.

This merged tag is what you access through `ctx.getSettings()` inside your perk callbacks.

### What each callback can do

| Callback | What you typically read | What you typically write |
|---|---|---|
| `conditions(ctx)` | `ctx.getSettings()` | Return `true` or `false` |
| `start(ctx)` | `ctx.getSettings()` | Persistent state in `ctx.getSettings()`, one-shot output in `ctx.getResult()` |
| `tick(ctx)` | `ctx.getSettings()`, `ctx.getElapsedTicks()` | Usually `ctx.getSettings()` for private lifecycle state |
| `stop(ctx)` | `ctx.getSettings()` | Cleanup in `ctx.getSettings()` |
| `status(ctx)` | `ctx.getSettings()` | UI lines via `addLine(...)` or `addLines(...)` |

Only `start()` has access to `ctx.getResult()`. PMMO merges whatever you write there back into the current perk execution for other perks to read. PMMO ignores the return values of `tick()` and `stop()`.

## PerkTagJS reference

`PerkTagJS` is the tag wrapper used in startup perks. It provides typed get/set methods instead of raw NBT manipulation.

### Reading values

- `keys()` — list all keys
- `has(key)` — check if a key exists
- `getString(key)`, `getStringOr(key, fallback)`
- `getInt(key)`, `getIntOr(key, fallback)`
- `getLong(key)`, `getLongOr(key, fallback)`
- `getFloat(key)`, `getFloatOr(key, fallback)`
- `getDouble(key)`, `getDoubleOr(key, fallback)`
- `getBoolean(key)`, `getBooleanOr(key, fallback)`
- `getOrCreateCompound(key)` — get or create a nested compound

### Writing values

- `remove(key)` — delete a key
- `clear()` — delete everything
- `putString(key, value)`
- `putBoolean(key, value)`
- `putInt(key, value)`
- `putLong(key, value)`
- `putFloat(key, value)`
- `putDouble(key, value)`
- `putCompound(key, value)`
- `putStringList(key, values)`
- `putNumberList(key, values)` — stores values as doubles
- `merge(value)` — merge another compound's keys into this one

### PMMO-specific helpers

- `getSkill()` — the skill name assigned to this perk
- `getResolvedLevel()` — the current player's level in that skill
- `getCooldown()` — the perk's cooldown in ticks
- `getDuration()` — the perk's duration in ticks
- `getChance()` — the perk's activation chance (0.0 to 1.0)

## Trigger context tags

`PmmoJS.trigger(...)` gives you a mutable `CompoundTag` through the event object. The lifecycle is straightforward:

1. PMMO prepares a trigger context tag
2. Your KubeJS script reads and mutates that tag
3. After your script returns, the mutated tag goes back to PMMO
4. PMMO can continue using that tag, including feeding it into perk execution

Use the event's `getContext*` / `putContext*` helper methods instead of editing the raw tag directly.

XP award helpers are also available: `getXpAwards()`, `setXpAwards(map)`, `setXpAward(skill, amount)`, `addXpAward(skill, amount)`, `clearXpAwards()`.

To cancel PMMO's processing for this trigger, call `event.setCancelled(true)`.

## Internal hook context tags

`PmmoJS.internal(...)` works similarly to triggers, but starts with a new empty `CompoundTag`. The bridge may seed that tag with hook-specific data before your script runs.

Key differences from triggers:

- Internal hooks start with an empty tag (triggers receive PMMO's prepared context)
- Internal hooks have action control methods: `event.skipPmmo()` (skip PMMO's handler), `event.deny()` (cancel the Forge action and skip PMMO)
- Some hooks get bridge-seeded keys: `EXPLOSION` gets `affectedBlockCount` and `affectedEntityCount`, `POTION_BREW` gets `alreadyTracked` and `markBrewed`

## Best practices

- Use `PerkTagJS` methods (like `getIntOr`, `putBoolean`) instead of raw NBT calls inside perk callbacks.
- Use `ctx.getSettings()` for state that later callbacks will need.
- Use `ctx.getResult()` only in `start()` for output that should flow into the current PMMO execution pass.
- For trigger and internal hook context, use the `getContext*` / `putContext*` helper methods on the event object.
- Only use raw `CompoundTag` when the API intentionally exposes it (e.g., `PmmoJS.xp(...)` or `PmmoHelper.registerTriggerListener(...)`).
